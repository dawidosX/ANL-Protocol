# ANL Protocol — analiza programu R6

**Audytowana paczka:** `ANL-Protocol-audyt-r6-91418cc.zip`  
**Deklarowany commit:** `91418cc436fde8b2e7e1fa829582f6947f840698`  
**Data analizy:** 2026-09-05

## Werdykt

**Na testnet / dalsze testy: TAK. Na immutable mainnet / audit-freeze: jeszcze NIE.**

Rdzeń programu jest obecnie znacznie mocniejszy niż w poprzednich rundach: poprawka `roll_day_and_write_checkpoint`, historyczne checkpointy, cap po `end_epoch`, ograniczenie Flexible do 365 dni, cooldown early-exit, walidacja mintów ANL/CAPY oraz rozdzielenie principal/reward/XNT/CAPY vaultów są sensownie zaprojektowane.

Znalazłem jednak co najmniej **jeden High oraz dwa nowe scenariusze ekonomiczne Medium**, plus poważny problem z provenance release.

| Waga | Problem | Ocena |
|---|---|---|
| **HIGH** | Publiczny `initialize` — pierwszy caller może zostać authority | **blokuje mainnet launch** |
| **MEDIUM** | Staker może wejść po `fund_xnt`, ale przed końcem doby i dostać część już istniejącego basketu | wymaga poprawki/testu |
| **MEDIUM** | Historyczny orphan można przechwycić przez stake **przed opóźnionym `settle_expired`** | poprawka R5 nie zamyka całego MEV |
| **MEDIUM / invariant** | Limit 200M ANL nie jest twardo egzekwowany | tokenomika może przekroczyć założony pool |
| **FREEZE BLOCKER** | źródła, test-log i `.so` są związane z różnymi commitami | obecnej binarki nie można przypisać do R6 |
| LOW/OPS | rozjazd Program ID + network features | poprawić przed release |
| Uwaga | implementacja nie zawsze robi 65/35 | dokumentacja i kod mówią co innego |

## 1. HIGH — `initialize` nadal może zostać przejęty

W `initialize.rs`:

```rust
pub struct Initialize<'info> {
    #[account(mut)]
    pub authority: Signer<'info>,
    ...
}
```

Nie ma związania `authority` z wcześniej ustalonym kluczem, upgrade authority ani żadnym commitmentem. Następnie:

```rust
cfg.authority = ctx.accounts.authority.key();
```

Czyli po świeżym deployu **pierwsza osoba, która skutecznie wywoła `initialize`, zostaje authority**.

Atakujący może przygotować własny fixed-supply ANL mint spełniający walidację, wyprzedzić transakcję inicjalizacyjną i utworzyć `global_config` PDA. Legalna inicjalizacja zespołu potem już nie przejdzie, bo PDA jest zajęte.

Dla już prawidłowo zainicjalizowanego testnetu okno ataku jest zamknięte. **Dla nowego Program ID na mainnecie traktowałbym to jako High.**

### Rekomendacja

`initialize` powinien wymagać z góry znanego inicjalizatora albo zweryfikować upgrade authority `ProgramData`.

Sama procedura „spróbujemy szybko zrobić initialize po deployu” jest słabszym zabezpieczeniem.

## 2. MEDIUM — stake po `fund_xnt` może dostać XNT sprzed wejścia

`fund_xnt` nie zwiększa od razu indeksu. XNT trafia do:

```rust
current_day_basket
```

i zostaje rozdzielone dopiero przy `close_day`.

Jeżeli użytkownik wchodzi **w tej samej dobie po wykonanym `fund_xnt`**, basket pozostaje otwarty. Następnie:

```rust
pool.total_shares += net;
...
pos.xnt_debt_index = pool.xnt_reward_index;
```

`xnt_reward_index` nie zawiera jeszcze istniejącego basketu.

### Kontrprzykład

```text
Alice ma 100 shares.

12:00 fund_xnt → current_day_basket = 100 XNT.
Indeks jeszcze się nie zmienił.

23:59 Bob stake'uje 100 shares.
Bob.debt = stary index.
total_shares = 200.

00:00 close/roll:
100 XNT / 200 shares.

Alice dostaje 50.
Bob dostaje 50.
```

Bob dostał połowę fundingu wykonanego **11 godzin przed jego wejściem**.

To przeczy intencji, że nowa pozycja nie powinna mieć roszczeń do XNT sprzed jej wejścia.

### Rekomendowany test

```text
stake Alice
fund_xnt(E)
stake Bob w tej samej epoce E
close_day(E)
assert Bob reward from funding before his stake == 0
```

## 3. MEDIUM — historyczny orphan można przechwycić przed `settle_expired`

R5 poprawił ważny problem. `settle_position_at` po zdjęciu wygasłej pozycji robi teraz:

```rust
self.redistribute_to_live(orphan)?;
```

zamiast zostawiać orphan dla przyszłego `close_day`.

Problem pozostaje jednak dla odwrotnej kolejności:

```text
Adam wygasł dawno temu, lecz nie został settled.
Po jego end_epoch były kolejne fundingi.

Celina stake'uje DZISIAJ.
Następnie Celina sama wywołuje permissionless settle_expired(Adam).
```

`settle_position_at(Adam)` obliczy historyczny orphan, zdejmie Adama i wykona:

```rust
redistribute_to_live(orphan)
```

A Celina jest już wtedy `live`.

W efekcie dostaje część XNT odpowiadającą okresowi, kiedy **w ogóle nie miała pozycji**.

To oznacza, że R5 usunął „staker wchodzący po settle”, ale nie „staker wchodzący przed opóźnionym settle”.

### Wniosek

Permissionless settlement może stworzyć ekonomiczny MEV:

```text
stake → settle starej wygasłej pozycji
```

Im bardziej opóźniony `settle_expired`, tym większy potencjalny historyczny orphan.

## 4. MEDIUM / invariant — limit 200M ANL nie jest twardo egzekwowany

`ANL_REWARD_POOL` jest stałe:

```rust
200_000_000 ANL
```

ale `stake` kontroluje głównie:

```rust
reward_vault.amount >= new_reserved
```

Nie ma twardego warunku:

```rust
total_anl_paid + anl_reward_reserved <= ANL_REWARD_POOL
```

Co więcej, tokeny mogą zostać przesłane bezpośrednio do Reward Vault poza `fund_rewards`.

Jeżeli vault będzie zawierał np. 300M ANL, kontrakt może potencjalnie zarezerwować i wypłacić więcej niż deklarowane 200M.

Kod po naruszeniu tylko alarmuje:

```rust
if total_anl_paid > ANL_REWARD_POOL {
    emit!(InvariantAlarm { ... });
}
```

czyli **wykrywa naruszenie po fakcie, ale go nie blokuje**.

### Efekt uboczny dla CAPY

Po przekroczeniu 200M:

```rust
remaining_anl =
    ANL_REWARD_POOL.saturating_sub(total_anl_paid)
```

daje `remaining_anl == 0`, więc dalsze nagrody ANL mogą otrzymać **0 CAPY**.

### Rekomendacja

Jeżeli 200M ma być częścią tokenomiki, powinien obowiązywać hard constraint:

```text
total_anl_paid
+ anl_reward_reserved
+ reward_now
<= 200M ANL
```

Saldo vaulta powinno zapewniać pokrycie, ale nie definiować maksymalnej emisji nagród.

## 6. LOW/OPS — Program ID / network features wymagają uporządkowania

W źródłach ten sam Program ID pojawia się dla różnych buildów sieciowych, podczas gdy konfiguracja Anchor wskazuje różne adresy dla środowisk.

Dodatkowo compile guard odrzuca część złych kombinacji feature’ów, ale nie wymusza jednoznacznie obecności dokładnie jednego network feature.

Nie widzę tu bezpośredniej ścieżki kradzieży środków, ale przed immutable mainnet takie niespójności należy usunąć.

---

## 7. Elementy ocenione pozytywnie

Mechanizm `roll_day_and_write_checkpoint` wygląda zdecydowanie lepiej od poprzedniej wersji:

- checkpointy są walidowane fail-closed,
- owner/PDA/version/epoch/pool-type są sprawdzane,
- `claim` i `settle_expired` wykonują roll przed capem,
- historyczne checkpointy ograniczają zależność wypłaty od kolejności transakcji.

Pozytywnie oceniam również:

- izolowane PDA vaultów,
- rozdzielenie principal/reward/XNT/CAPY,
- Token-2022 allowlist dla ANL/CAPY,
- brak mint/freeze authority ANL,
- brak mint authority CAPY,
- coverage nagród ANL,
- osobny `claim_capy`,
- historyczny łańcuch checkpointów,
- brak pętli po wszystkich pozycjach w jednej instrukcji,
- limit Flexible 365 dni,
- cooldown early-exit.

# Finalna decyzja

## Audit-freeze / immutable mainnet: **NIE**

Przed freeze rekomenduję zamknąć:

1. publiczny `initialize`,
2. scenariusz `fund_xnt → stake → close_day`,
3. scenariusz `stake → delayed settle_expired → orphan`,
4. twardy limit 200M ANL,
5. pełny provenance dla jednego HEAD,
6. jednoznaczne Program ID / network build config.

Po tych zmianach sensowna będzie bardzo wąska **R7** skupiona wyłącznie na:

- nowych kontrprzykładach ekonomicznych,
- provenance,
- finalnym reproducible buildzie,
- gotowości do immutable mainnet.

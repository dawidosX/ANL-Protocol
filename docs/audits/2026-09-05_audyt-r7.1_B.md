## Pytania celowane

### 1. `max(ckpt, debt)` — underpay / nadpłata okna

**Czyste.**

`cap_index_at` (`lifecycle.rs` ~124–133) zwraca `ck.index.max(pos.xnt_debt_index)`.

`ck.index < debt` jest możliwe tylko gdy checkpoint ostatniego fundingu ≤ `target` został sfinalizowany **zanim** `redistribute_to_live` podbił indeks, a pozycja weszła **po** tym bumpie. Taka pozycja nie siedziała w `total_shares` przy rozdziale koszyka tej doby — pending 0 jest poprawne, nie zaniża należnej zafundowanej doby.

Jeśli pozycja weszła przed `close_day` zafundowanej doby: `debt ≤ index_przed_close`, finalny checkpoint ≥ `debt`. `max` nie obcina.

**Okna Genesis:** `accrued_to_cap` z `cap = max(ckpt, debt)` daje 0, gdy ckpt < debt. Przy `already == 0` → `NothingToClaim`. Nie powstaje `to_pay > 0` z samego `max`.

Nadpłata okna wymagałaby `cap >` faktyczny index doby `prog_epoch`. `max` nigdy nie podnosi ponad `max(ckpt, debt)`; `ckpt` to ostatni funding ≤ `prog_epoch` (łańcuch `next`). Brak wektora nadpłaty.

`claim_genesis_window` nadal ma `checked_sub(already)` (`lifecycle.rs` ~601–604). Przy `already > 0` i cap zaciśniętym do debt dostałby Overflow — ale kolejny blok okna musi użyć **ostatniego** fundingu ≤ nowego `prog_epoch`. Po udanym pierwszym oknie ten checkpoint ma index ≥ debt. Ścieżka jest marginalna; finalny `claim` używa `saturating_sub`. **Uwaga UX**, nie finding.

### 2. Obrona w głąb — konserwacja pending + orphan

**Czyste.**

`settle_position_at` (`state/mod.rs` ~213–238): `cap' = cap.max(debt)`.

- `pending = (cap' − debt) × s / P`
- `orphan = (live − cap') × s / P` (`saturating_sub` gdy live < cap' — wtedy orphan 0)

Suma floorów ≤ `(live − debt) × s / P`. Różnica = dust 0 lub 1 jednostka na pozycję. Po zdjęciu shares: orphan → `redistribute_to_live` albo `xnt_undistributed` gdy `total_shares == 0`. Token w vaultcie nie znika. Property test R6 + `test_r7_cap_ponizej_debt_daje_zero_bez_overflow` pokrywają gałąź cap < debt.

### 3. `write_final_index` tylko przy domknięciu

**Czyste.**

`add_to_basket` zwraca `Some(current_day)` tylko gdy `current_day != epoch && basket > 0` (`state/mod.rs` ~136–153). `fund_xnt` woła `write_final_index` wyłącznie wtedy (`fund.rs` ~403–420).

Ścieżka z briefu: funding doby K, potem roll w `stake` bez `prev_day_ckpt` → helper wymaga checkpointu gdy roll zamyka koszyk → `CheckpointRequired`, tx pada, koszyk **nie** znika bez zapisu. Potem `fund_xnt(K+1)` może zamknąć K i zapisać finalny index w **tej** tx. Nie zostaje bazowy index jako cap.

Doba zamknięta przez `stake`/`claim`/`close_day` ma już finalny index z chwili close (przed późniejszymi redystrybucjami). Kolejny `fund_xnt` jej nie nadpisuje — to właśnie fix R6-02.

Checkpoint doby **bieżącej** (`genesis_ckpt.index = live` po `add_to_basket`) nadal trzyma index **przed** close tej doby. Cap settlementu po rollu używa last_closed, nie otwartej doby. Zgodnie z modelem.

### 4. Pin `initialize`

**Czyste w buildzie sieciowym; Uwaga na ceremonię mainnet.**

`#[cfg(any(network-mainnet, network-testnet))]` + `EXPECTED_INIT_AUTHORITY` (`initialize.rs` ~72–77, `constants.rs` ~37–41).

`init_*_vault` / `create_pool` wymagają istniejącego `GlobalConfig` i `has_one = authority`. Nie da się utworzyć vaultu ani puli przed `initialize`. Wyścig first-come na świeżym Program ID: tylko klucz pinu przechodzi w artefakcie testnet/mainnet.

Testy integracyjne **bez** feature sieci — pin wyłączony (zamierzone). Strażnik wartości stałej w `init_authority_pinned_*`.

Mainnet: stała = ten sam hot key co testnet (`Dx2v…zvEm`). Zmiana na multisig = nowy sha binarki. **F-02 zostaje blockerem mainnetu**, nie freeze logiki testnet.

### 5. Limit 200M vs CAPY vs vault

**Czyste.**

`stake.rs` ~173–179: `total_anl_paid + new_reserved ≤ ANL_REWARD_POOL` oraz saldo vault ≥ reserved.

- `unstake_early` zdejmuje `anl_reward` z reserved → limit znów się otwiera.
- CAPY: `remaining_anl = POOL.saturating_sub(total_anl_paid)`. Przy `paid + reserved = POOL` remaining ≥ suma jeszcze niewypłaconych `anl_reward`. Brak dzielenia przez 0 (`remaining == 0` ⇒ entitlement 0, tylko gdy paid ≥ POOL).
- `fund_rewards` ponad 200M: nadmiar zostaje pokryciem / dustem w Reward Vault. Nie zwiększa emisji. Środki „uwięzione” ponad 200M wypłat — decyzja operacyjna fundera, nie drenaż.

### 6. borsh 0.9.3 / 9 advisory

**Czyste (nieosiągalne z SBF naszego ABI), z zastrzeżeniem stosu.**

Konta: `u8/u16/u32/u64/u128/i64/bool/Pubkey/enum/[u8;N]` — brak `Vec<ZST>`. Anchor 0.30 deserializuje borsh 0.10. Moduł `solana_program::borsh0_9` nie jest wołany z instrukcji. RUSTSEC-2023-0033 nie ma powierzchni w naszych `#[account]`.

`bincode` unmaintained — brak znanego exploita na tym ABI. Reszta listy = host / `solana-client` / program-test (`cfg(not(target_os = "solana"))`).

Cel „pusta lista advisory” wymaga upgrade'u Solana/Anchor **przed immutable mainnet** — nie blocker freeze testnet.

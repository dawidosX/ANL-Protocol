# 1. Co zostało już uznane za poprawione

W R7.1 wprowadzono poprawki dotyczące wcześniejszych findingów:

1. `cap_index_at` stosuje:
   ```rust
   max(checkpoint.index, position.xnt_debt_index)
   ```

2. Defense-in-depth powtarza clamp do `debt` w settlement/accrual.

3. `fund_xnt` zapisuje finalny checkpoint tylko wtedy, kiedy faktycznie doszło do domknięcia poprzedniej doby.

4. `initialize` dla buildów:
   - `network-testnet`
   - `network-mainnet`

   wymaga `EXPECTED_INIT_AUTHORITY`.

5. `stake` egzekwuje twardy limit:
   ```text
   total_anl_paid + anl_reward_reserved <= ANL_REWARD_POOL
   ```

6. Dodano provenance:
   - `src_tree`
   - `code_tree`
   - `math_tree`
   - SHA binarki
   - pełny git bundle

# 2. Najważniejsze rzeczy do niezależnego sprawdzenia

## A. BUILD WITHOUT `network-*` — potencjalny bypass pina `initialize`

To jest obecnie najważniejszy punkt do potwierdzenia lub obalenia.

Pin inicjalizatora jest aktywny warunkowo:

```rust
#[cfg(any(feature = "network-mainnet", feature = "network-testnet"))]
```

Sprawdź, czy build bez żadnego:

```text
network-mainnet
network-testnet
```

nadal się kompiluje.

Jeżeli tak, sprawdź czy w takim buildzie:

```text
EXPECTED_INIT_AUTHORITY
```

nie jest egzekwowane.

### Pytanie bezpieczeństwa

Czy przypadkowe lub błędne:

```bash
anchor build
```

może stworzyć deployowalną binarkę z tym samym `declare_id!`, ale bez ochrony first-come `initialize`?

Jeżeli TAK:

- oceń severity,
- pokaż dokładny attack/release path,
- zaproponuj fail-closed compile guard,
- zaproponuj regression test/CI guard.

Preferowane zachowanie:

```text
dokładnie jeden network profile musi być aktywny
```

albo jawny osobny profil lokalny.

---

## B. Provenance `.so` ↔ source tree

Sprawdź skrypty pakujące/release.

W szczególności zweryfikuj, czy `pack-audit.sh`:

1. rebuildzi `.so`,
2. czy tylko bierze istniejący plik z:
   ```text
   target/deploy/anl_staking.so
   ```
3. czy sprawdza, że SHA binarki pochodzi z bieżącego `src_tree`,
4. czy porównuje:
   ```text
   current src_tree
   current code_tree
   current math_tree
   ```
   z release manifestem.

### Potencjalny problem

Możliwa sekwencja:

```text
build commit A
→ powstaje target/deploy/anl_staking.so

checkout commit B
→ kod się zmienia

pack-audit.sh
→ pakuje commit B
→ hashuje stare .so z A
```

Jeżeli skrypt tego nie wykryje, provenance nie jest fail-closed.

### Oczekiwany fix

Pakowanie powinno abortować, jeśli:

```text
src_tree != release_manifest.src_tree
code_tree != release_manifest.code_tree
math_tree != release_manifest.math_tree
sha256(local .so) != release_manifest.sha256
```

Sprawdź również, czy pełny łańcuch:

```text
git bundle
→ commit
→ source tree
→ build
→ .so
→ on-chain dump
```

jest rzeczywiście odtwarzalny z dostarczonych artefaktów.

# 3. Re-audyt zmian R6 → R7.1

## 3.1 `max(checkpoint, debt)`

Sprawdź wszystkie miejsca użycia capu.

Dowiedź albo obal:

```text
effective_cap = max(checkpoint.index, debt)
```

nie może:

- nadpłacić pozycji,
- zaniżyć legalnej należności,
- spowodować double claim,
- wytworzyć sztucznego orphan,
- spowodować underflow/overflow,
- zmienić Genesis window w sposób prowadzący do nadpłaty.

Szczególnie sprawdź:

```text
claim
claim_genesis_window
settle_expired
accrued_to_cap
settle_position_at
```

---

## 3.2 Conservation law

Dla pozycji:

```text
pending + orphan
```

powinno odpowiadać ekonomicznie:

```text
(index - debt) × shares
```

z dokładnością do integer floor/dust.

Sprawdź wszystkie gałęzie:

- `cap < debt`
- `cap == debt`
- `cap > debt`
- ostatnia pozycja w puli
- `total_shares == 0` po zdjęciu pozycji
- orphan → live holders
- orphan → undistributed

---

## 3.3 Final checkpoint

Sprawdź, czy po zmianie `add_to_basket -> Option<closed_epoch>` istnieje jakakolwiek sekwencja, w której:

```text
checkpoint epoki E
```

pozostaje na indeksie bazowym mimo tego, że basket E został już ekonomicznie rozdzielony.

Szczególnie:

```text
fund_xnt(E)
roll przez stake/claim/settle
fund_xnt(E+1)
```

oraz przypadki:

```text
basket == 0
basket > 0
total_shares == 0
```

# 4. Znane residuale — spróbuj je exploitować

Nie zakładaj, że są bezpieczne.

## 4.1 Stake po `fund_xnt` tej samej doby

Obecny design świadomie pozwala, by pozycja otwarta po fundingu, ale przed końcem doby, uczestniczyła w koszyku tej doby.

Sprawdź:

- czy można to wykorzystać ekonomicznie,
- czy koszt locku faktycznie neutralizuje MEV,
- czy da się połączyć to z Flexible/early unstake,
- czy daje się zbudować strategię dodatniej wartości oczekiwanej.

---

## 4.2 Delayed `settle_expired` i orphan

Sprawdź sekwencję:

```text
A wygasa
settle nie jest wykonywany przez długi czas
B stake
B wywołuje settle_expired(A)
```

Czy B może przejąć część historycznego orphana?

Jeżeli TAK:

- policz konkretny scenariusz,
- oceń severity,
- oceń, czy bot SLA `close_day → settle` jest wystarczającą kontrolą,
- rozstrzygnij czy to inherentna semantyka czy exploitowalny MEV.

---

## 4.3 Genesis windows bez rolla

`claim_genesis_window` nie robi rolla.

Sprawdź:

```text
stale current_day
checkpoint istnieje, ale jest jeszcze bazowy
basket nie został rozdzielony
claim_genesis_window
```

Czy może być:

- permanent underpay,
- overpay,
- `window_claimed > final accrued`,
- późniejszy underflow,
- tylko tymczasowy underpay, który final claim sam koryguje?

Pokaż dowód albo kontrprzykład.

# 5. 200M ANL

Sprawdź twardy invariant:

```text
total_anl_paid + anl_reward_reserved <= 200M ANL
```

we wszystkich ścieżkach:

- stake
- claim
- settle
- early unstake
- normal maturity
- reward vault overfunding
- direct token transfer do vaulta

Sprawdź również CAPY:

```text
remaining_anl = ANL_REWARD_POOL - total_anl_paid
```

i wszystkie warunki dzielenia.

Dowiedź, że nie da się:

- zarezerwować >200M,
- wypłacić >200M,
- zablokować entitlementów błędnym denominator,
- uzyskać CAPY po wyczerpaniu limitu w niespójny sposób.
